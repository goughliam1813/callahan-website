Install

Quartet QE needs Java 21 or newer. Pick one way in.

In Claude Code

Nothing to clone. Run these in Claude Code; it then asks for your tests folder and, if you want them, your Jira, Azure DevOps, GitHub, GitLab and Jenkins details.

Claude Code
/plugin marketplace add Callahan-ci/quartet-qe
/plugin install quartet-qe@quartet-qe

In the Claude desktop app

Download the .mcpb file for your computer from the latest release (mac-arm64 for Apple silicon, mac for Intel, linux or linux-arm64), double-click it and fill in the settings.

From source

terminal
git clone https://github.com/Callahan-ci/quartet-qe.git
cd quartet-qe
./get-started.sh

get-started.sh checks your machine, builds the tool and offers a menu: watch the demo, connect your chat tool, or set up tests for your own product.

Your first run

The fastest way to see it work is the demo shop that ships with Quartet. In one terminal start the shop and leave it running; in another, run a story.

terminal 1
./demo-shop.sh
terminal 2
./quartet-qe run --story stories/SHOP-142.md

It ends with a summary like this, and a review page to open:

output
Context  26 files, 12 engineering principles
Story    SHOP-142: Checkout reserves stock and confirms the order (7 acceptance criteria)
Tests    6 written: 6 passed, 0 failed, 0 skipped
Review   reports/SHOP-142/review.html (ready to merge)

Create a tests repo for your product

Tests live in their own repo, one per product or team.

terminal
./new-tests-repo.sh ../my-product-tests
cd ../my-product-tests

You get quartet.yaml, a context/ folder for your environment, and space for tests, recordings and reports. Quartet itself is installed once per machine, so nothing else is copied in.

In a chat tool, the quickest start is to say "Help me set up Quartet QE for my product." It asks what it needs, writes the files and checks each connection. When it needs a token it names the variable and you run ./quartet-qe secret NAME in a terminal, so secrets never go through the chat.

Tell it what it can reach

One file lists every system the tests may touch, and a guard that keeps them off anything else. Target types are api, screen (web and mobile), kafka, postgres and mongo. Databases are read-only unless a target says otherwise, and secrets come from environment variables, never from the file.

context/environments/default.yaml
name: default
guard:
  production: false
  allowHosts: [localhost, staging.example.com]   # tests can only reach these hosts
targets:
  orders-api:
    type: api
    description: Orders REST API.
    baseUrl: "${ORDERS_API_URL:-http://localhost:8080}"
    context: [contracts/openapi/orders-service.yaml]
  orders-db:
    type: postgres
    description: Orders database, read-only for tests.
    url: "${ORDERS_DB_URL:-jdbc:postgresql://localhost:5432/orders}"

Put OpenAPI specs, Pact files and event schemas under context/contracts/ and point targets at them with context:. The AI reads them before it writes a test, which is the single biggest improvement you can make.

Write a story

A story is a markdown file in stories/. Write acceptance criteria a person could check: a number, a status, a screen, an event. Vague criteria get questions back, not tests.

stories/SHOP-142.md
# SHOP-142: Checkout reserves stock and confirms the order

As a customer I want my items reserved when I check out, so that I am never sold something that is out of stock.

## Acceptance criteria

- AC1: A valid order for in-stock items returns 201 with status RESERVED and is persisted in the orders database.
- AC2: An order exceeding available stock is rejected with 409 INSUFFICIENT_STOCK and stock does not change.

Check a story before you spend any AI on it, from a file or straight from your tracker:

terminal
./quartet-qe check-story --story stories/SHOP-142.md
./quartet-qe check-story --story jira:SHOP-142     # also ado:123, github:45, gitlab:7

Write and run the tests

In a chat tool, say "Write tests for stories/SHOP-142.md using Quartet QE." With an API key instead, run:

terminal
./quartet-qe run --story stories/SHOP-142.md

This is the one step that uses the AI. It reads your context and the story, writes the tests, checks them against your engineering principles, asks for an independent second opinion, runs them, records each verified step, and writes reports/SHOP-142/review.html.

Add --prove to plant bugs in a test build and check the tests catch them. It is slower, and worth doing before you trust a suite.

Review, then replay with no AI

Open the review page: anything that needs your attention is at the top. Read the tests like any other code, then commit the tests and the recordings/ folder together. From then on:

terminal
./gradlew test            # replays from recordings, no AI
./gradlew test -Pwatch    # the same, in a visible browser you can follow
output
[quartet] Recordings: 8 replayed, 0 handed off, 0 missed | AI: 0 model calls

If a step breaks after a redesign, ./quartet-qe repair records it again. It can change how a step is done, never what the test must prove; if the product itself is wrong, you get a bug report instead.

How to test a website

Add a screen target with a desktop browser, then write the story as you would explain it to a colleague. The test names the target and says what the user does; the AI works out the clicks the first time.

context/environments/default.yaml
targets:
  shop-web:
    type: screen
    description: The customer web shop, served at /.
    baseUrl: "${SHOP_WEB_URL:-http://localhost:18080}"
    devices:
      desktop: {kind: web, engine: chromium}
CheckoutReservesStockTest.java
@Test
@AcceptanceCriteria("AC6")
void customerSeesConfirmationInTheWebShop(TestAgent agent) {
    ActResult order = agent.act("Order 1 unit of SKU-1001 as customer C-7 through the web shop",
            why("Most customers place their orders through the web shop"),
            on("shop-web"),
            returns("orderNumber"));
    assertThat(order.get("orderNumber")).matches("ORD-[0-9]+");

    agent.verify("The page tells the customer their order is reserved",
            why("Customers need reassurance that the purchase worked"),
            on("shop-web"));
}

To test a public site with no setup at all, say "Test my site https://www.example.com using Quartet QE" in your chat tool. Quartet creates the environment for that site (desktop, iPhone and Android phone, allowing only that site) and drafts the story with you.

How to test phone browsers

Phone browsers need nothing extra. Add devices to the same target and mark the test with @OnEverySurface; it runs once per device, each with its own recording.

context/environments/default.yaml
targets:
  shop-web:
    type: screen
    baseUrl: "https://staging.example.com"
    devices:
      desktop: {kind: web, engine: chromium}
      iphone: {kind: web, engine: webkit, preset: iphone}
      android-phone: {kind: web, engine: chromium, preset: android}
      android-device: {kind: android}   # an emulator or phone listed by adb
CheckoutReservesStockTest.java
@OnEverySurface("shop-web")   // runs once per device above
@AcceptanceCriteria("AC6")
void customerSeesConfirmationInTheWebShop(TestAgent agent) {
    ActResult order = agent.act("Order 1 unit of SKU-1001 as customer C-7 through the web shop",
            why("Most customers place their orders through the web shop"),
            on("shop-web"),
            returns("orderNumber"));
    assertThat(order.get("orderNumber")).matches("ORD-[0-9]+");
}

How to test a native Android app

Quartet drives a native app through adb and the app's accessibility tree, the way a screen reader does. Nothing is installed on the device; there is no Appium server to run.

  1. Install the Android SDK platform tools and set ANDROID_HOME.
  2. Start an emulator or plug in a phone with the app installed, and check adb devices lists it.
  3. Add a screen target with the app's package name and an android device.
  4. Write the story, then run it as usual.
context/environments/default.yaml
targets:
  calculator-app:
    type: "screen"
    description: "The Fossify Calculator Android app"
    app:
      android: "org.fossify.math"
    devices:
      android:
        kind: "android"   # an emulator or phone listed by adb
terminal
adb devices                 # the emulator or phone must be listed
./quartet-qe observe --target calculator-app --device android   # see what the agent sees
CalculatorTest.java
@Test
@AcceptanceCriteria("AC1")
void addingTwoNumbersShowsTheirSum(TestAgent agent) {
    ActResult shown = agent.act("Open the calculator, enter 7 + 8, press equals and read the result shown",
            why("A user adding two numbers must get the right answer"),
            on("calculator-app"),
            returns("text"));
    assertThat(shown.get("text")).isEqualTo("15");
}

@Test
@AcceptanceCriteria("AC6")
void aFinishedCalculationAppearsInHistory(TestAgent agent) {
    ActResult entry = agent.act("Open the calculator, calculate 12 + 34, open History and read the newest entry",
            why("A user must be able to find an earlier calculation"),
            on("calculator-app"),
            returns("text"));
    assertThat(entry.get("text")).contains("12+34").contains("46");
}

This is from a real run against Fossify Calculator on an emulator. The story had six acceptance criteria; the AI wrote six tests; all six passed and the review said ready to merge. Each test starts the app cold, and once recorded they replay with no AI.

iOS apps use a small XCTest runner in native/ios and need Xcode. It is newer and has not yet been proven on a real run.

How to test APIs, databases and Kafka

One test can follow a piece of work through every system it touches. Each act names its target; the test holds no URLs, SQL or topic names, only intent.

context/environments/demo.yaml
targets:
  orders-api:
    type: api
    baseUrl: "${ORDERS_API_URL:-http://localhost:18080}"
    context: [contracts/openapi/orders-service.yaml]
  orders-db:
    type: postgres
    url: "${ORDERS_DB_URL:-jdbc:postgresql://localhost:15432/postgres}"
  order-events:
    type: kafka
    brokers: "${KAFKA_BROKERS:-localhost:19092}"
    schemas:
      shop.orders.created: contracts/events/order-created.schema.json
CheckoutReservesStockTest.java
@Test
@AcceptanceCriteria({"AC1", "AC2"})
void orderFlowsThroughApiDatabaseAndEvents(TestAgent agent) {
    ActResult order = agent.act("Place an order for 2 units of SKU-1001 for customer C-42",
            why("A customer checking out is the start of the reservation journey"),
            on("orders-api"),
            returns("orderId", "status"));
    assertThat(order.get("status")).isEqualTo("RESERVED");

    ActResult saved = agent.act("Find order {{orderId}} in the orders database",
            with("orderId", order.get("orderId")),
            why("A reserved order must survive beyond the request"),
            on("orders-db"),
            returns("status", "customer_id"));
    assertThat(saved.get("status")).isEqualTo("RESERVED");

    ActResult event = agent.act("Find the order created event for order {{orderId}}",
            with("orderId", order.get("orderId")),
            why("Downstream teams rely on this event to fulfil the order"),
            on("order-events"),
            returns("found", "schemaValid"));
    assertThat(event.getBool("schemaValid")).isTrue();
}

Use agent.verify(claim, on(target)) to check a claim against a system, such as a row in a database or an event on Kafka. MongoDB works the same way with a mongo target.

Run it in Jenkins

Put your Jenkins address, user and API token in connectors.yaml, then:

terminal
./quartet-qe setup-jenkins

It writes the Jenkinsfile if the repo has none and creates a multibranch pipeline job pointed at your repo. Every build replays the recorded steps with no AI, so the pipeline needs no AI key. To open a pull request with the review as its description:

terminal
./quartet-qe publish --story jira:SHOP-142 --code github

When something goes wrong

What you seeWhat to do
No AI configuredUse your chat AI, or run ./quartet-qe ai-key.
A test fails with no recordingRun ./quartet-qe run once, or use QUARTET_MODE=auto.
A step fails after a UI changeRun ./quartet-qe repair --file <Test.java> --selector '<package>.*'.
A host is blockedAdd it to allowHosts in your environment file, if you really mean to test it.
Anything elseRun ./quartet-qe doctor; it checks your setup and says what to fix.
