Four worked examples, taken from real Quartet QE repos: the story, the one file you edit, the test the AI wrote, and what you get back.

1You write the story
stories/CALC-1.md
# CALC-1: A user can do everyday sums and look them up again

As a user of the Fossify Calculator app on my Android phone,
I want quick, correct arithmetic and a record of what I calculated.

## Acceptance criteria

- AC1: Entering 7 + 8 and pressing equals shows the result 15.
- AC4: Pressing C once after entering 1234 removes only
  the last digit, leaving 123.
- AC6: After calculating 12 + 34, the History screen
  lists 12+34 with its result 46.
2You say what it can reach
context/environments/default.yaml
targets:
  calculator-app:
    type: "screen"
    description: "The Fossify Calculator Android app"
    app:
      android: "org.fossify.math"
    devices:
      android:
        kind: "android"   # an emulator or phone listed by adb
3The AI writes the test
CalculatorTest.java (2 of 6 tests)
@Test
@AcceptanceCriteria("AC1")
void addingTwoNumbersShowsTheirSum(TestAgent agent) {
    ActResult shown = agent.act("Open the calculator, enter 7 + 8, press equals and read the result shown",
            why("A user adding two numbers must get the right answer"),
            on("calculator-app"),
            returns("text"));
    assertThat(shown.get("text")).isEqualTo("15");
}

@Test
@AcceptanceCriteria("AC6")
void aFinishedCalculationAppearsInHistory(TestAgent agent) {
    ActResult entry = agent.act("Open the calculator, calculate 12 + 34, open History and read the newest entry",
            why("A user must be able to find an earlier calculation"),
            on("calculator-app"),
            returns("text"));
    assertThat(entry.get("text")).contains("12+34").contains("46");
}
4You read the result

Ready to merge.

  • 6 acceptance criteria, 6 tests, 6 passed
  • Recorded on an Android emulator, then replayed with no AI
  • No selectors, XPath, element IDs or Appium server

A real run against Fossify Calculator, an open-source Android app.

Quartet reads the app through the device's accessibility tree over adb, so nothing is installed on the phone. How to test an Android app

# SHOP-142: Checkout reserves stock and confirms the order

As a customer I want my items reserved when I check out,
so that I am never sold something that is out of stock.

## Acceptance criteria

- AC6: A customer ordering in the web shop is shown
  a confirmation with the order number.
2You say what it can reach
context/environments/demo.yaml
targets:
  shop-web:
    type: screen
    description: The customer web shop, served at /.
    baseUrl: "${SHOP_WEB_URL:-http://localhost:18080}"
    devices:
      desktop: {kind: web, engine: chromium}
3The AI writes the test
CheckoutReservesStockTest.java
@Test
@AcceptanceCriteria("AC6")
void customerSeesConfirmationInTheWebShop(TestAgent agent) {
    ActResult order = agent.act("Order 1 unit of SKU-1001 as customer C-7 through the web shop",
            why("Most customers place their orders through the web shop"),
            on("shop-web"),
            returns("orderNumber"));
    assertThat(order.get("orderNumber")).matches("ORD-[0-9]+");

    agent.verify("The page tells the customer their order is reserved",
            why("Customers need reassurance that the purchase worked"),
            on("shop-web"));
}
4You read the result

Ready to merge.

  • A real browser, a screenshot at every step
  • agent.verify checks what the customer is told
  • The assertion is plain Java: the AI never marks its own work

How to test a website

1You write the story
stories/SHOP-142.md
# SHOP-142: Checkout reserves stock and confirms the order

## Acceptance criteria

- AC1: A valid order for in-stock items returns 201 with
  status RESERVED and is persisted in the orders database.
- AC2: The order is published on shop.orders.created with
  the matching orderId and conforms to the event schema.
2You say what it can reach
context/environments/demo.yaml
targets:
  orders-api:
    type: api
    baseUrl: "${ORDERS_API_URL:-http://localhost:18080}"
    context: [contracts/openapi/orders-service.yaml]
  orders-db:
    type: postgres
    url: "${ORDERS_DB_URL:-jdbc:postgresql://localhost:15432/postgres}"
  order-events:
    type: kafka
    brokers: "${KAFKA_BROKERS:-localhost:19092}"
    schemas:
      shop.orders.created: contracts/events/order-created.schema.json
3The AI writes the test
CheckoutReservesStockTest.java
@Test
@AcceptanceCriteria({"AC1", "AC2"})
void orderFlowsThroughApiDatabaseAndEvents(TestAgent agent) {
    ActResult order = agent.act("Place an order for 2 units of SKU-1001 for customer C-42",
            why("A customer checking out is the start of the reservation journey"),
            on("orders-api"),
            returns("orderId", "status"));
    assertThat(order.get("status")).isEqualTo("RESERVED");

    ActResult saved = agent.act("Find order {{orderId}} in the orders database",
            with("orderId", order.get("orderId")),
            why("A reserved order must survive beyond the request"),
            on("orders-db"),
            returns("status", "customer_id"));
    assertThat(saved.get("status")).isEqualTo("RESERVED");

    ActResult event = agent.act("Find the order created event for order {{orderId}}",
            with("orderId", order.get("orderId")),
            why("Downstream teams rely on this event to fulfil the order"),
            on("order-events"),
            returns("found", "schemaValid"));
    assertThat(event.getBool("schemaValid")).isTrue();
}
4You read the result

Ready to merge.

  • One test follows the order through the API, Postgres and Kafka
  • No URLs or SQL in the test: it states intent
  • The OpenAPI contract and event schema are read first

How to test phone browsers

One run, four stops.

The AI does the thinking once. After that, the recording does the work.

Story

Type it, point at a file, or pull a ticket from Jira, Azure DevOps, GitHub or GitLab.

Tests

The AI reads your contracts, telemetry and principles, reuses your steps, then writes and validates the tests.

Replay

The recording is the test. Reruns, in CI or on a laptop, use no AI.

Every run after

Go

An independent review and a traceability matrix on one page. A person approves.

Every line it runs on.

One story can cross the app, the services behind it and the data they leave.

LineWhat it checks
Native Android appsTaps, types and checks inside the app itself.
WebsitesA real browser, with a screenshot at every step.
Phone browsersThe same story on mobile browsers.
APIsCalls checked against your API descriptions.
KafkaPublishes, consumes and checks what arrived.
Postgres and MongoDBThe data a feature left behind.
Your toolsStories from Jira, Azure DevOps, GitHub and GitLab. Reports into Jenkins.

Reports you can hand over.

Every run writes a branded, self-contained report. Open it in a browser, attach it to a ticket, or publish it from Jenkins.

ResultsEach test against the story it came from, in a traceability matrix.
ScreenshotsA picture of every step, for each target.
ReviewAn independent check that reads the tests before they run.
JenkinsThe report publishes into your build page.

It runs on your machine.

Within limits you can read and check.

AccountNone. No server of ours and no usage tracking.
ToolsEach tool is labelled read-only, destructive or open-world, so the app can ask before anything risky.
FilesAccess is confined, symlinks are checked and credential files are refused.
SecretsTokens go in the plugin or extension settings, never through the chat.
ReleasesSHA-256 checksums, a software bill of materials and GitHub build provenance.

In Claude Code, add the marketplace, then install. The settings dialog asks for your tracker and Jenkins details.

/plugin install quartet-qe@quartet-qe
